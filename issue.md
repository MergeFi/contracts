Overview
docs/refund-permissionless-analysis.md's closing section, "Cross-contract inconsistency (noted, not fixed here)," states plainly:

milestones::cancel_milestone and maintenance-pool::withdraw are both strictly admin-only with no timeout/escape-hatch concept at all — unlike escrow, a sponsor whose milestone or maintenance-pool admin goes permanently unresponsive has no path to recover undistributed funds except an off-chain intervention... This issue is that dedicated design issue, filing the exact gap the doc identified and explicitly declined to file itself.

Confirmed by reading both functions directly: cancel_milestone (contracts/milestones/src/lib.rs:187-214) requires require_admin(&env)?.require_auth() unconditionally — there is no branch, no timestamp check, nothing resembling escrow's refund's if now < escrow.deadline { admin required } pattern (contracts/escrow/src/lib.rs:161-166). withdraw (contracts/maintenance-pool/src/lib.rs:116-157) is the same — unconditional admin gate, no deadline concept exists anywhere in MaintenancePool's fields (contracts/maintenance-pool/src/types.rs:8-17 has no deadline-shaped field at all) or Milestone's (contracts/milestones/src/types.rs:7-19, same).

The consequence, stated precisely: a sponsor who deposits into a milestone or maintenance pool and later finds the admin/backend permanently unresponsive (operator ceased operations, lost its key, etc. — exactly the scenario docs/refund-permissionless-analysis.md argues escrow's permissionless refund exists to protect against) has zero on-chain recourse for milestones' remaining_budget or a maintenance pool's balance. This is a strictly worse position than an escrow sponsor in the identical scenario, purely because of which of the three contracts they happened to use — an inconsistency in the sponsor-protection guarantee across contracts that are otherwise marketed as three equally-trustworthy instruments in the same platform.

The doc explicitly flags why this needs product input rather than being a pure engineering call: "what would 'deadline' even mean for an open-ended, repeatedly-topped-up maintenance pool?" — milestones has a natural analog (a deadline set at create_milestone, mirroring escrow's fund), but maintenance-pool's "recurring, never finishes" design (per its own module doc, contracts/maintenance-pool/src/lib.rs:1-8) genuinely doesn't have an obvious single point to hang a deadline off of, since new deposits can arrive at any time from any sponsor.

Requirements
milestones: add a deadline field to Milestone, set at create_milestone (mirroring escrow's fund), and a permissionless-after-deadline path on cancel_milestone (or a new function) that refunds remaining_budget to sponsor exactly as escrow's refund does, without requiring admin authorization once expired. Consider whether allocated-but-unreleased amounts should also become recoverable this way, which directly intersects with the companion "no deallocate/reallocate" issue filed in this batch — the two should likely be designed together rather than independently, since a timeout-triggered milestone wind-down needs to decide the same "what happens to allocated-not-released issues" question that a manual cancel_milestone today leaves ambiguous (tracked by #5).
maintenance-pool: since a single global deadline doesn't fit the "recurring, per-deposit" model, consider a per-deposit or per-sponsor reclaim mechanism instead — e.g. each individual Deposit record (already timestamped, contracts/maintenance-pool/src/types.rs:21-25) becomes permissionlessly reclaimable by its original sponsor after some fixed inactivity window (no withdraw against that pool for N ledgers), rather than a single deadline for the whole pool. This is a genuinely harder design problem than milestones' case and may need explicit product sign-off on the semantics (e.g., does reclaiming a deposit require the pool's aggregate balance to still cover it, given deposits aren't earmarked individually today?).
Whatever mechanism is chosen, ensure it's sponsor-authorized only when triggered before the timeout (mirroring escrow's extend_deadline pattern for "let the sponsor delay their own recovery window if they still trust the admin"), and permissionless-but-still-sponsor-destined only after it (mirroring refund's exact security property: anyone can trigger it, but funds only ever go to the address on record).

 milestones: deadline field + permissionless-after-expiry recovery path implemented, tested
 maintenance-pool: some form of per-deposit or per-sponsor timeout-based recovery implemented, tested — or an explicit, reasoned deferral written up if genuinely still blocked on product input

#41 escrow::fund + milestones::create_milestone permanently retire issue_id/milestone_id after any terminal state — no re-funding path
Repo Avatar
MergeFi/contracts
Overview
escrow::fund and milestones::create_milestone both gate on the existence of their storage key, not on the record's status: fund rejects with AlreadyFunded whenever env.storage().persistent().has(&DataKey::Escrow(issue_id)) is true (contracts/escrow/src/lib.rs:78-81), and create_milestone does the identical thing with DataKey::Milestone(milestone_id) and Error::IssueAlreadyAllocated (contracts/milestones/src/lib.rs:67-70 — note this reuses the IssueAlreadyAllocated variant for a milestone-level collision, not an issue-level one, which is itself a minor error-naming mismatch worth fixing alongside this issue).

Neither check is ever undone. Once an Escrow/Milestone record is written, it is never deleted, and its key is never freed, regardless of what status it later reaches. A Funded escrow that gets Refunded (contracts/escrow/src/lib.rs:147-180) or Paid (contracts/escrow/src/lib.rs:107-143) still has env.storage().persistent().has(&key) == true forever after — the record's status field changes, but its presence never does. The same is true for a cancel_milestoned milestone (contracts/milestones/src/lib.rs:187-214, sets closed = true, never removes the record).

Consequence: once a bounty's issue_id (or a release's milestone_id) reaches any terminal state — paid, refunded, or cancelled — that identifier is permanently retired. There is no way, ever again, to call fund/create_milestone for that same issue_id/milestone_id, even by the exact same, legitimate sponsor, even if the reason for wanting to re-fund it is completely ordinary: a bounty expired unresolved and got refunded, then the maintainer reopens the GitHub issue and the sponsor wants to fund it again; or a release's milestone was cancelled early and the team wants to restart it under the same identifier for continuity with existing off-chain references. Neither contract offers any path back — the sponsor's only option is to have mergefi-backend mint a new issue_id/milestone_id for what is, off-chain, the same GitHub issue/release, silently breaking whatever 1:1 mapping the backend's database assumes between on-chain identifiers and GitHub entities.

This stands in explicit contrast to maintenance-pool::deposit, which was deliberately designed to support unlimited repeat use of the same pool_id (contracts/maintenance-pool/src/lib.rs:57-110, no existence-based rejection — a pool can be deposited into indefinitely, which is the whole point of it being "recurring, open-ended" per the contract's own module doc). The asymmetry across the three contracts here isn't discussed anywhere in the README or either audit doc.

This is distinct from #1 (escrow::fund issue-id squatting via front-running), which is about an unrelated third party claiming an id before the legitimate sponsor. This issue is about the legitimate sponsor being permanently unable to reuse an id they already, correctly, funded once and saw through to a terminal state.

Requirements
Decide and document the intended product semantics: should a terminal-state issue_id/milestone_id ever be reusable? If yes, design how (e.g. allow fund/create_milestone to proceed if the existing record's status is terminal, overwriting it — carefully confirming this can't be abused to overwrite a record mid-flight, i.e. still in Funded/open status). If the answer is genuinely "no, identifiers are meant to be one-shot forever," document that explicitly in the README so mergefi-backend's identifier-minting strategy can rely on it deliberately rather than accidentally.
If reuse is supported, ensure re-funding a previously-terminal escrow/milestone correctly resets all relevant fields (status, created_at, and for milestones, remaining_budget/closed/allocations) rather than partially inheriting stale data from the prior lifecycle.
Whichever direction is chosen, add an explicit test locking in the behavior, since none currently exists either way.
Acceptance Criteria
 Product/design decision documented (reuse supported vs. permanently one-shot by design)
 If reuse is implemented: fund/create_milestone allow re-funding a terminal-status record, correctly resetting state, implemented in both contracts
 If reuse is explicitly rejected: README's "Contracts" sections updated to state this plainly, so it's a documented constraint rather than a silent gap
 Test(s) added either way (test_fund_rejects_reuse_of_refunded_issue_id / test_fund_allows_reuse_after_refund, and the create_milestone analog)
 cargo test --workspace passes
Additional Notes
Precise references: contracts/escrow/src/lib.rs:78-81 (fund's existence check), contracts/milestones/src/lib.rs:67-70 (create_milestone's, reusing IssueAlreadyAllocated — consider renaming/adding a MilestoneAlreadyExists variant, since the current error name is actively misleading for this specific rejection path, referring to an "issue" when the collision is at the milestone level).
Test sketch: test_fund_rejects_reuse_after_terminal_refund — fund(issue_id=1, ...), let deadline pass, refund(1) (now Refunded), attempt fund(1, ...) again with fresh, valid arguments and the same legitimate sponsor's own authorization — assert it still fails with AlreadyFunded, proving the identifier is dead regardless of who's asking or why. If the fix direction is "support reuse," invert the assertion and add the state-reset checks described above.
Cross-references: #1 (front-running squatting — different actor, different mechanism, same storage-key gate); the crowdfunding-support issues filed later in this batch (any multi-sponsor design for escrow/milestones will need to decide how identifier reuse interacts with a mid-flight cancelled crowdfund, making this issue's product decision a prerequisite for that one).

#38 All three contracts: instance storage (Admin/Treasury/FeeBps) TTL is never extended — risk of full contract archival, not just per-record
Repo Avatar
MergeFi/contracts
Overview
None of the three contracts ever extend the TTL of their own instance storage — the storage tier holding DataKey::Admin, DataKey::Treasury, and DataKey::FeeBps. I confirmed this by grepping for every extend_ttl call site across all three lib.rs files: every single call is env.storage().persistent().extend_ttl(...) (contracts/escrow/src/lib.rs:333, contracts/milestones/src/lib.rs:314, contracts/maintenance-pool/src/lib.rs:182), applied only to individual persistent records (Escrow/Milestone/Pool/Deposit/IssueStatus keys). There is no env.storage().instance().extend_ttl(...) call anywhere in any of the three contracts.

This is a different and more severe failure mode than #11 ("Fixed TTL extension thresholds risk archival/fund-inaccessibility for long-lived escrows and pools"). #11 is about the fixed (100_000, 500_000) thresholds being non-adaptive for individual persistent records that don't get written to often enough. This issue is about instance storage never being extended at all — not even with a fixed, non-adaptive threshold. On Soroban, a contract's instance storage entry has its own TTL, and once it expires past the archival point, the contract is archived: every single invocation — including get_admin, get_escrow, release, refund, literally everything, since require_admin and every get_* view function reads instance storage — fails until a RestoreFootprint operation is submitted for that specific ledger key. Unlike an individual expired Escrow record (which only makes that one issue_id unreadable), instance storage archival takes down the entire contract instance for every issue/milestone/pool it has ever held, simultaneously.

Instance storage TTL in Soroban does not receive any special automatic extension just because other storage tiers (persistent, per-key) are being written to in the same invocation — each storage instance/entry manages its own TTL independently, and instance storage specifically requires an explicit extend_ttl call (or a bump via stellar contract extend/equivalent off-chain tooling) to stay alive. Since none of the three contracts' Rust code contains this call, the only thing currently keeping any of the three deployed testnet contracts' instance storage alive is whatever initial TTL was granted at deploy/initialize time (visible in the README's "Deployed on Stellar testnet" table) — and nothing in Makefile, scripts/deploy.mjs, or scripts/invoke.mjs performs any periodic instance-TTL bump either.

Requirements
Add env.storage().instance().extend_ttl(threshold, extend_to) calls to all three contracts, at minimum on every state-changing entrypoint (mirroring how per-record extend_ttl is called on every write today), so that ongoing contract usage keeps the instance alive.
Additionally consider extending instance TTL on get_* view calls too, since a contract that's still being read frequently (e.g. by the backend's sync loop, per README "Backend integration" step 5) but not written to for a long stretch would otherwise still silently drift toward archival under a write-only extension strategy.
Determine and document the actual practical runway this buys given Stellar's ~5s ledger close time (see the companion extend_deadline/TTL-math issue for the exact conversion), and whether the same threshold/extend-to values used for persistent per-record TTLs are appropriate for instance storage, or whether instance storage — being far higher-consequence to lose — warrants a larger extend_to margin.
Document, in the README's "Data models" section (which currently only describes per-record TTL: extend_ttl(..., 100_000, 500_000)), that instance storage requires and now receives its own independent extension, and what happens (and who is responsible for RestoreFootprint) if it's ever allowed to lapse anyway.
Acceptance Criteria
 instance().extend_ttl(...) added to all state-changing entrypoints (and ideally view functions) in all three contracts
 Chosen threshold/extend-to values documented with reasoning distinct from the per-record values
 Test(s) using env.ledger().with_mut(...)/env.storage().instance().extend_ttl testutils (or equivalent TTL-inspection testutils available in soroban-sdk 26.1.0) confirming instance TTL is actually bumped after a representative write call in each contract
 README updated to describe instance-storage TTL handling explicitly
 cargo test --workspace passes
Additional Notes
Confirmed via grep -rn "extend_ttl" contracts/*/src/lib.rs — 18 total call sites across the three contracts, all persistent().extend_ttl, zero instance().extend_ttl.
This is the highest-blast-radius TTL gap in the codebase: an expired persistent record (#11's scope) strands one issue/milestone/pool's funds; an expired instance record (this issue's scope) strands every record the contract has ever held, and also breaks every read (get_admin, get_treasury, get_fee_bps, and by extension every get_escrow/get_milestone/get_pool/get_deposit call too, since those go through the same contract instance) until someone submits a RestoreFootprint — a capability not mentioned anywhere in this repo's README.md, Makefile, or scripts/.
Test sketch: test_instance_storage_ttl_is_extended_on_write — after initialize, read the instance entry's live-until ledger via the testutils TTL inspection API (env.storage().instance().get_ttl() or the equivalent in this SDK version — verify exact API against soroban-sdk = "26.1.0"'s docs, since exact method names have shifted across SDK versions); advance the ledger sequence close to expiry; call a write function (fund/allocate/deposit); confirm the live-until value increased. A companion negative test — advance past the current (pre-fix) implicit expiry with no writes and confirm the contract becomes genuinely unusable — is valuable to include as a regression guard demonstrating the bug this issue fixes, even though simulating true archival inside testutils::Env may require Soroban's dedicated ledger-snapshot/restore testing utilities rather than plain set_timestamp/set_sequence_number.
Cross-references: #11 (per-record TTL, a related but distinct and lower-blast-radius gap); the companion extend_deadline-TTL-math issue filed in this same batch (which quantifies the ~29-day real-world runway of the existing per-record extend_to value, useful context for choosing instance storage's own extend-to margin); #15 (upgrade/migration path — any future upgrade mechanism will also need to think about instance-storage TTL continuity across an upgrade).

#43 milestones: no deallocate/reallocate mechanism — #5's pending fix will make a bad allocate() call permanently unrecoverable
Repo Avatar
MergeFi/contracts
Overview
milestones has exactly three functions that touch an issue_id's allocation: allocate (reserve), release_issue (pay out), and (indirectly) cancel_milestone (closes the whole milestone). There is no deallocate, reallocate, or reduce_allocation function anywhere (grep -n "fn " contracts/milestones/src/lib.rs lists only initialize, create_milestone, allocate, release_issue, cancel_milestone, and the get_* views).

allocate (contracts/milestones/src/lib.rs:92-128) is a strictly one-way operation: once called for a given issue_id, it moves amount from remaining_budget into milestone.allocations (line 116-117) and writes IssueStatus::Allocated (lines 121-125), and there is no way to undo just that one allocation. If the admin fat-fingers the issue_id (allocates to the wrong GitHub issue) or the amount (over- or under-provisions relative to what was actually agreed), the funds are committed to that specific issue_id slot permanently, with only one way out: calling release_issue for that issue_id — which pays out to whatever recipients the admin supplies at that point, i.e. the only "correction" available is paying the wrong-issue allocation to someone anyway, not un-committing it back to remaining_budget for correct reallocation.

This is worse than it looks today, and is about to get worse still. cancel_milestone (contracts/milestones/src/lib.rs:187-214) only refunds remaining_budget — the unallocated remainder — back to the sponsor; it does nothing for issues that are Allocated but not yet Released. Right now, because release_issue doesn't check milestone.closed (the exact gap tracked by #5), a cancelled milestone's allocated-but-unreleased issues can still be released — which today functions as the only remaining correction mechanism for a bad allocation: cancel the milestone, then have the admin release_issue the mis-allocated amount to whoever is actually owed it, salvaging the situation. The moment #5 is fixed as currently scoped (making release_issue respect milestone.closed), this salvage path closes: a cancelled milestone's allocated-but-unreleased funds become 100% permanently unrecoverable — not refundable via cancel_milestone (only touches remaining_budget), not releasable via release_issue (blocked by the closed check), and not deallocatable back to remaining_budget (no such function exists). The README's own Roadmap section anticipates exactly this gap ("Support partial milestone/pool refunds and issue re-allocation (currently allocate is one-shot per issue)") without connecting it to what #5's fix will do to the one currently-working escape hatch.

Requirements
Add a deallocate(milestone_id, issue_id) function: admin-only, moves an Allocated-status (not yet Released) issue's amount back into milestone.remaining_budget, removes the entry from allocations, and clears its IssueStatus. Must reject if the issue is already Released (funds have left the contract, nothing to reclaim) or not currently allocated at all.
This should land before or alongside #5's fix, not after — implementing #5's closed check on release_issue without also shipping a deallocation path would (as described above) convert a currently-recoverable-via-workaround state into a permanently-stuck one. The PR that closes #5 should explicitly confirm this issue is resolved first, or resolve both together.
Also consider whether allocate itself should support amending an existing allocation's amount directly (a combined "deallocate-then-reallocate" convenience), though a standalone deallocate plus the existing allocate (which already rejects IssueAlreadyAllocated on a fresh call, so would need to permit re-allocation post-deallocation) covers the core need.
Acceptance Criteria
 deallocate implemented: admin-only, rejects Released issues, rejects non-Allocated issues, correctly restores remaining_budget and clears allocations/IssueStatus
 Confirmed compatible with #5's eventual fix — either landed first, or explicitly coordinated in the same change
 Test: test_deallocate_restores_remaining_budget_and_allows_reallocation (allocate, deallocate, confirm remaining_budget is restored, confirm the same issue_id can be allocated again with a corrected amount)
 Test: test_deallocate_rejects_already_released_issue
 Test proving the specific stranding scenario this issue is about no longer occurs post-fix: allocate, cancel_milestone, deallocate the still-allocated issue, confirm the amount returns to a refundable state (either directly, or via a subsequent cancel_milestone-style sweep if the milestone is already closed — needs a decision on whether deallocate is callable after closed, since that's precisely the scenario this issue exists to unblock)

Additional Notes
Precise references: allocate at contracts/milestones/src/lib.rs:92-128; cancel_milestone at contracts/milestones/src/lib.rs:187-214 (refund logic at lines 201-209, scoped strictly to remaining_budget); release_issue's missing closed check is the exact code path this issue's "about to get worse" analysis depends on, tracked at #5.
